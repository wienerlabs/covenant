# Covenant Security Audit — Findings

> Produced by an 8-lens multi-agent hunt (on-chain Anchor, authz, payments, injection/SSRF, crypto, DoS, business-logic, web-hardening). The adversarial verification pass was interrupted by transient server rate-limiting, so these are the raw finder outputs; each was triaged by hand before fixing. Counts below are pre-dedup.

**Totals:** {'critical': 3, 'high': 19, 'medium': 19, 'low': 20, 'info': 3}


## CRITICAL

### requireAuth never binds the proven signer to the body wallet — systemic IDOR even when AUTH_ENFORCED=true
- **File:** `app/lib/require-auth.ts:80-121 (consumed by jobs, stake, faucet, disputes, claims/buy, etc.)`
- **Category:** IDOR / broken access control  ·  **Confidence:** high
- **What:** requireAuth verifies that the caller controls SOME wallet (valid Ed25519 signature over the request, or a valid API key) and returns { wallet }. But NO route ever compares __auth.wallet to the wallet identity in the request body (posterWallet / takerWallet / walletAddress / buyerWallet / arbitratorWallet). `grep -rn 'auth.wallet' app/api` returns zero matches. The canonical message in canonicalAuthMessage() binds method+path+bodyHash+ts but NOT the acting identity, and the route logic trusts the body field for all authorization decisions (job.posterWallet === posterWallet, takerWallet ownership, faucet target, etc.). So any party holding a single valid keypair (or, worse, any shared API key in API_KEYS) can sign a request and put a DIFFERENT victim wallet in the body, acting as that victim.
- **Exploit:** 1. Operator flips AUTH_ENFORCED=true believing the app is now safe. 2. Attacker controls wallet A (any keypair) and signs a valid request for POST /api/jobs/[id]/submit. 3. Attacker sets takerWallet=VICTIM in the body. requireAuth passes (signature valid for A), and the route only checks that a JobInterest exists for takerWallet=VICTIM — it never checks that A == VICTIM. Attacker submits/cancels/finalizes/disputes on behalf of arbitrary wallets, drains the faucet to wallets they don't own, mints reputation, etc. With a shared API key the attacker bypasses the signature entirely and impersonates everyone.
- **Fix:** After requireAuth, when mode==='signature' enforce that __auth.wallet === the body's acting-wallet field for every route (e.g. require __auth.wallet === posterWallet in /jobs/[id]/dispute, === takerWallet in /jobs/[id]/submit, === walletAddress in /faucet & /agents/stake, === buyerWallet in /claims/[id]/buy). Bake the acting wallet into the canonical signed message (add it to canonicalAuthMessage) so it cannot be swapped. For api_key mode, scope the key to specific wallets rather than treating it as a global act-as-anyone credential.

### AUTH_ENFORCED defaults OFF — every 'protected' mutating route is fully unauthenticated in production
- **File:** `app/lib/require-auth.ts:25-27,84`
- **Category:** Missing authentication  ·  **Confidence:** high
- **What:** authEnforced() returns true only when process.env.AUTH_ENFORCED === 'true'. It is not set in .env or .env.example, so requireAuth returns { ok: true, mode: 'disabled' } unconditionally. Every route that relies solely on requireAuth for auth — /api/jobs (POST), /api/jobs/[id]/accept, /submit, /dispute, /finalize, /api/agents/stake, /api/faucet, /api/disputes (POST), /api/claims/[id]/buy — performs no identity check at all by default. The only gate left is IP rate limiting and the on-chain tx verification on routes that have it.
- **Exploit:** With the shipped/default config, an unauthenticated attacker POSTs directly to e.g. /api/faucet { walletAddress: <any> } (mints 100 test USDC to any wallet, rate-limited only by IP), or /api/agents/stake { walletAddress: <victim>, amount } to inflate/alter a victim's stake record, or /api/jobs/[id]/submit with an arbitrary takerWallet on any agent/bot job that lacks a PDA (isHumanFlow false path skips on-chain check) to forge deliveries and reputation. No signature, key, or wallet proof is required.
- **Fix:** Default-deny: make authEnforced() return true unless explicitly disabled (e.g. AUTH_DISABLED==='true' for local dev only), or hard-require it in production builds. Fail closed on mutating financial/identity endpoints regardless of the flag.

### Body-supplied wallet identity is never bound to the authenticated signer (auth bypass across all routes)
- **File:** `app/lib/require-auth.ts:80-121`
- **Category:** fee-bypass / impersonation  ·  **Confidence:** high
- **What:** requireAuth returns `{ok:true, wallet}` for the signature path but NONE of the audited routes compare that authenticated `wallet` to the wallet field in the request body. dispute/route.ts checks `job.posterWallet !== posterWallet` where `posterWallet` comes from the body; reviews/route.ts trusts body `posterWallet`/`takerWallet`; claims/[id]/buy trusts body `buyerWallet`; agents/stake trusts body `walletAddress`; faucet trusts body `walletAddress`. Because requireAuth is also a complete no-op unless `AUTH_ENFORCED=true` (line 84), and even when enforced any wallet with a valid signature over the request can pass an arbitrary other wallet in the body, the 'Only the poster can…' / 'Only the seller can…' guards are decorative — they only check that the body string equals a DB column the attacker can read.
- **Exploit:** With AUTH_ENFORCED unset (default), an attacker calls any mutating endpoint with no auth headers at all and simply sets posterWallet/takerWallet/buyerWallet/walletAddress to the victim's address. e.g. POST /api/reviews with the real poster's wallet to leave reviews; POST /api/agents/stake crediting a victim; POST /api/faucet for any wallet. Even with AUTH_ENFORCED=true, attacker signs with their OWN wallet but puts the victim's wallet in the body — the route never cross-checks signer==body wallet.
- **Fix:** In each mutating route, after requireAuth succeeds in signature mode, assert auth.wallet === body.<actorWallet> (posterWallet/takerWallet/buyerWallet/sellerWallet/walletAddress). Make AUTH_ENFORCED the default. For faucet/stake/reviews specifically, derive the acting wallet from auth.wallet rather than trusting the body.


## HIGH

### Wallet-signature auth has no per-signature replay protection (replayable within 5-minute window)
- **File:** `app/lib/wallet-auth.ts:33-115 (and app/lib/require-auth.ts:80-121)`
- **Category:** missing replay/nonce protection  ·  **Confidence:** high
- **What:** verifyWalletSignature freshness relies solely on a +/-5 minute timestamp skew window (MAX_TIMESTAMP_SKEW_MS, wallet-auth.ts:9,71). There is no nonce, jti, or consumed-signature store. requireAuth() builds a canonical message binding method+path+bodyHash+ts (require-auth.ts:107-117) but never records that a given (signature, ts) was already used. The same signed header (x-wallet, x-signature, x-timestamp) verifies as valid every time it is presented for up to 5 minutes. Because the body hash and path are part of the message, an attacker who captures one authenticated mutating request can replay that EXACT request arbitrarily many times during the window (e.g. resubmit a job, trigger a dispute, fire any idempotency-sensitive state change repeatedly).
- **Exploit:** 1. Attacker observes/MITMs (or reads logs/proxy with) one authenticated mutating request: headers x-wallet, x-signature, x-timestamp plus the raw body. 2. Within 5 minutes, attacker re-sends the identical HTTP request (same method, path, body, and the three headers) N times. 3. verifyWalletSignature returns ok:true each time because the timestamp is still within skew and the signature matches the message; no nonce/used-signature check exists. 4. Any side-effecting endpoint (dispute open, job submit, profile mutation) is executed N times by the victim's identity.
- **Fix:** Add a durable, atomic consumed-signature store keyed on the signature (or a hash of wallet|ts|signature), checked-and-inserted via a unique-constraint INSERT (like x402-payments.claimPayment). Reject when the key already exists. Alternatively/additionally require a server-issued single-use nonce in the canonical message. The store entries can expire after the skew window. Wire this into requireAuth before returning ok:true.

### SSRF: TOCTOU / DNS-rebinding gap between assertPublicUrl and the verification fetch in agent registration
- **File:** `/Users/baturalpguvenc/covenant/app/app/api/agents/register/route.ts:40-90`
- **Category:** SSRF  ·  **Confidence:** high
- **What:** POST /api/agents/register validates endpointUrl with assertPublicUrl() (which resolves DNS and rejects private targets) at line 40, then performs a separate fetch(endpointUrl) at line 82. The fetch re-resolves the hostname independently, so the address that was validated is not the address that is connected to. A DNS name whose record flips between the validation lookup and the fetch (DNS rebinding, low-TTL record, or round-robin where only one A record is public) bypasses the guard and lets the server issue a POST to an internal host. The endpoint is reached as a POST with a JSON body, making it a usable SSRF gadget against internal services that accept POST. There is also no authentication on this route, so any anonymous caller can drive these outbound requests.
- **Exploit:** 1. Attacker controls evil.example.com with a 0-second TTL. 2. Configure it to resolve to a public IP for the first lookup (passing assertPublicUrl) and to 169.254.169.254 / 10.x / 127.0.0.1 for the second lookup. 3. POST /api/agents/register with endpointUrl=http://evil.example.com and valid name/description/capabilities. 4. assertPublicUrl resolves the public IP and passes; fetch() at line 82 re-resolves to the internal IP and the server POSTs to the internal target, reaching cloud metadata or internal-only POST endpoints. The response status leaks via the 422/2xx branch.
- **Fix:** Resolve the hostname once, assert every returned address is public, and pin the connection to that validated IP (e.g. resolve manually then fetch using the IP with a Host header, or use an HTTP agent with a lookup callback that enforces isBlockedIp on the address actually dialed). Re-validate inside a custom dns.lookup hook on the fetch/undici dispatcher so the address connected to is the address checked. Also require authenticated/wallet-signed registration and rate-limit the outbound test fetch.

### Missing authorization: any user can overwrite any wallet's profile avatar (stored data: URL)
- **File:** `/Users/baturalpguvenc/covenant/app/app/api/profile/[wallet]/avatar/route.ts:8-67`
- **Category:** Broken access control / IDOR  ·  **Confidence:** high
- **What:** POST /api/profile/[wallet]/avatar takes the target wallet from the URL path and writes imageData straight into Profile.avatarUrl (prisma.profile.update where walletAddress = wallet) with no proof the caller owns that wallet — no signature, session, or ownership check. The only gate is a hardcoded block on two agent wallets. The stored value is an attacker-supplied data:image/... string up to ~500KB that is later rendered as <img src> across the app (chat, battle, agents pages). An attacker can deface any user's avatar and persist large blobs in the DB for every wallet.
- **Exploit:** 1. Pick any victim wallet address W. 2. POST /api/profile/W/avatar with JSON {"imageData":"data:image/png;base64,<attacker image>"}. 3. The server updates W's profile with no ownership check; the victim's avatar is replaced site-wide. Repeat across many wallets to bloat the DB (each row ~500KB) toward the storage quota.
- **Fix:** Require the caller to prove ownership of `wallet` before writing — verify a wallet signature over a server-issued nonce (the app already does signature verification for payments) or a session bound to that wallet. Reject if the authenticated wallet != path wallet. Additionally cap stored avatar size hard and prefer storing to Blob over inlining base64 in the DB.

### Unauthenticated profile avatar overwrite (IDOR) — any wallet's avatar can be set by anyone, with SVG/HTML payload accepted
- **File:** `app/app/api/profile/[wallet]/avatar/route.ts:8-67`
- **Category:** Broken Access Control / IDOR + Stored content injection  ·  **Confidence:** high
- **What:** POST /api/profile/[wallet]/avatar takes the target wallet purely from the URL path and never verifies the caller controls that wallet. There is no requireAuth() / verifyWalletSignature() call (unlike jobs/disputes/claims routes which all import requireAuth). Any unauthenticated caller can overwrite the avatarUrl of ANY existing profile. The only validation is `imageData.startsWith("data:image/")`, which permits `data:image/svg+xml;base64,...`. The full data URL is stored verbatim in Profile.avatarUrl and later rendered (app/battle/page.tsx:2678,2708 etc. via <img src={agent.avatarUrl}>). SVG inside an <img> tag does not execute script in modern browsers, so this is not a direct DOM-XSS, but it is (a) an authorization break letting attackers deface arbitrary user/agent profiles and (b) stored attacker-controlled markup that becomes dangerous the moment any view switches to <object>/<iframe>/<embed> or a direct link to the data URL.
- **Exploit:** 1. Attacker enumerates a victim wallet address (public on leaderboard/jobs). 2. `curl -X POST https://app/api/profile/<victimWallet>/avatar -H 'content-type: application/json' -d '{"imageData":"data:image/svg+xml;base64,<base64 of a defacement/phishing SVG up to ~500KB>"}'`. 3. prisma.profile.update succeeds with no auth; victim's avatar is now attacker-controlled across the whole app. Repeat in a loop to mass-deface every profile.
- **Fix:** Gate the route behind requireAuth() and assert the authenticated wallet equals the path wallet: `const raw = await req.text(); const auth = await requireAuth(req,{rawBody:raw}); if(!auth.ok) return 401; if(auth.mode==='signature' && auth.wallet!==wallet) return 403;`. Additionally reject `data:image/svg+xml` (allowlist raster types png/jpeg/webp/gif only) so no attacker markup is ever stored. Note requireAuth is a no-op until AUTH_ENFORCED=true, so also add an explicit ownership/signature check that does not depend on that flag.

### Unauthenticated, unthrottled file upload to Vercel Blob (delivery/upload) — storage/cost abuse
- **File:** `app/app/api/delivery/upload/route.ts:17-141`
- **Category:** Missing authentication / Resource abuse  ·  **Confidence:** high
- **What:** POST /api/delivery/upload writes arbitrary caller-supplied bytes (up to 5MB) to the project's Vercel Blob store using the privileged BLOB_READ_WRITE_TOKEN, with no authentication, no rate limiting, and no content-type/extension allowlist. file.type and file.name are taken straight from the multipart part (lines 57-58) and used as the stored content-type and as part of the blob path. There is no requireAuth() call. Anyone on the internet can upload unlimited 5MB objects, burning storage and bandwidth billing, and can set an arbitrary Content-Type (e.g. text/html) on a stored object.
- **Exploit:** Loop: `for i in $(seq 1 100000); do curl -F file=@5mb.bin https://app/api/delivery/upload; done` — fills the blob store and runs up Vercel storage/egress bills with zero credentials. Or upload `file` with name `x.html` and type `text/html` to host arbitrary HTML on the blob domain.
- **Fix:** Wrap in requireAuth() (read raw body once) and add per-IP/per-wallet rate limiting. Enforce a content-type allowlist and sanitize/normalize filename + extension (do not trust file.type / file.name). Consider deriving content-type server-side from magic bytes rather than the client header.

### Unauthenticated, unthrottled image generation (generate/image) — paid fal.ai API abuse

### POST /api/agents/stake — write/increment stake for any wallet (auth is no-op + unbound)

### POST /api/agents/register — register agents under any wallet, no auth + SSRF probe primitive
- **File:** `app/app/api/agents/register/route.ts:17-150`
- **Category:** Missing authentication / impersonation  ·  **Confidence:** high
- **What:** No requireAuth and no rate limiter. walletAddress comes from the body and the agent is persisted with verified:true after a server-side test POST to endpointUrl. The 5-agents-per-wallet cap is keyed on the attacker-supplied walletAddress, providing no protection.

### PATCH/DELETE /api/hosted-agents/[id] — ownership check is spoofable (compares stored wallet to body wallet, no auth)
- **File:** `app/app/api/hosted-agents/[id]/route.ts:17-75`
- **Category:** IDOR / broken access control  ·  **Confidence:** high
- **What:** PATCH and DELETE 'authorize' by reading the agent row and checking agent.walletAddress === body.walletAddress. Since the attacker supplies walletAddress in the body and the owner wallet is readable (GET /api/hosted-agents/[id] and GET /api/hosted-agents return walletAddress), the attacker simply sets walletAddress to the real owner's address. There is no signature/key proving control of that wallet.

The equality check passes because the attacker echoed the owner's address.

### Expensive fal.ai image generation endpoint has no auth and no rate limit
- **File:** `app/app/api/generate/image/route.ts:35`
- **Category:** unauthenticated-expensive-call  ·  **Confidence:** high
- **What:** POST /api/generate/image accepts an arbitrary prompt and, on every request, calls fal.ai's flux/schnell model (paid per generation), then downloads the result, hashes it, and uploads it to Vercel Blob (paid storage + egress). There is no authentication, no payment gate, and no rate limit anywhere in the handler. The only input check is `prompt.length >= 5`. This is a public Next.js route, so it is directly reachable by anyone.
- **Exploit:** An attacker runs `for i in $(seq 1 100000); do curl -X POST https://host/api/generate/image -d '{"prompt":"anything here"}' & done`. Each call burns a paid fal.ai inference and a Vercel Blob PUT. Thousands of concurrent calls run up the FAL_KEY bill, exhaust the fal.ai quota (denying the legitimate design-agent flow that depends on it), and fill Blob storage — a direct financial-DoS / quota-exhaustion attack with no credential required.
- **Fix:** Gate the route: require an authenticated session or an internal-only secret (it is only called server-side from hosted-agents chat via internal fetch, so it can be locked to an internal secret / same-origin check), AND add a durable per-IP and per-wallet rate limit via `enforceIpLimit(req, ...)` / `rateLimitDurable`. Add a hard cap on prompt length and reject when FAL quota guard trips.

### A2A JSON-RPC endpoint creates Job rows with no auth and no rate limit
- **File:** `app/app/api/a2a/route.ts:6`
- **Category:** unauthenticated-write-dos  ·  **Confidence:** high
- **What:** POST /api/a2a is a public JSON-RPC endpoint with no authentication and no rate limiting. The `task/create` method inserts a new Job row (`prisma.job.create`) for every request, with attacker-controlled `capability`, `input`, `minWords`, and `specJson`. Nothing limits how many jobs a caller can create or how large `input` is (it is round-tripped through `JSON.parse(JSON.stringify(input))` and stored as JSON).
- **Exploit:** An attacker loops `curl -X POST https://host/api/a2a -d '{"jsonrpc":"2.0","id":"x","method":"task/create","params":{"input":{...huge blob...}}}'`. Each call writes a Job row with `posterWallet:"aip-external"`. Unbounded calls flood the Job table (storage exhaustion, pollutes the open-jobs feed that autonomous/arena bots scan, drives DB row-count toward the quota the cron/db-quota job watches), and large `input` payloads bloat each row. No spoofing or credential needed.
- **Fix:** Add `enforceIpLimit(req, ...)` (durable per-IP limit) at the top of the handler, authenticate the caller (the a2a protocol supports DIDs/signatures — verify them), bound the size of `params.input` before persisting, and cap jobs-per-window per caller.

### Per-IP rate limits on expensive AI routes are defeated by a spoofed X-Forwarded-For header
- **File:** `app/lib/rateLimit.ts:185`
- **Category:** rate-limit-bypass  ·  **Confidence:** medium
- **What:** `ipFromRequest()` and the inline IP extraction in several routes take the client IP from `x-forwarded-for` (first element) / `x-real-ip` with no trust boundary. Every expensive AI route keys its rate limiter solely on this value: hosted-agents chat (route.ts:52-56 `chat:${ip}`), hosted-agents test (route.ts:25-26 `agent-test:${ip}`), autonomous/run (route.ts:46-48 `autonomous:${ip}`), arena/run (route.ts:75-78 `arena:${ip}`), battle/run (route.ts:72-74 `battle:${ip}`). On Vercel the platform overwrites XFF at the true edge, but if the app is ever fronted by another proxy, run on a different host, or the value is otherwise client-influenced, the header is attacker-controlled. Each of these routes makes one or more Anthropic API calls per request.
- **Exploit:** Attacker sends each request with a fresh forged header: `curl -X POST https://host/api/hosted-agents/test -H 'x-forwarded-for: 1.2.3.4' ...` then `5.6.7.8`, etc. Because the limiter bucket is `agent-test:<spoofed-ip>`, every request lands in a brand-new bucket and the 10/min cap never triggers. The attacker drives unlimited Claude (Haiku/Sonnet/Opus) inferences across chat/test/arena/autonomous/battle, exhausting the Anthropic credit/quota and racking up cost — financial DoS. The same applies to faucet_ip and battle-chat keys.
- **Fix:** Derive the client IP from a trusted source only: use the platform-provided connection IP (`req.ip` on Vercel / the right-most XFF hop after the known proxy count), not the left-most client-supplied entry. Combine IP with an authenticated principal (wallet + verified signature) in the rate-limit key so an anonymous attacker cannot mint unlimited buckets, and prefer requiring auth/payment on every route that calls the LLM.

### Off-chain dispute on demo/no-PDA jobs is free and permanently blocks finalize (griefing)
- **File:** `app/app/api/jobs/[id]/dispute/route.ts:124-168`
- **Category:** dispute-griefing  ·  **Confidence:** high
- **What:** The on-chain raise_dispute verification (verifyTxInvokedCovenant + JobEscrow status/bond/reasonHash checks) is gated entirely on `if (job.pda)` (line 136). Jobs created via the `demoMode` path in app/app/api/jobs/route.ts:389-420 and all SOL jobs (line 282-310) are persisted with NO `pda` and `escrowLocked:false`. For those jobs the txHash is still 'required' (line 124) but `verifyTxInvokedCovenant(txHash)` is called with an attacker-supplied string, and because there is no pda the on-chain JobEscrow assertions are skipped. ### init_config accepts unbounded/unsafe parameters (no upper bound on bond bps, no max_challenge_period ceiling, no min_bond sanity)
- **File:** `/Users/baturalpguvenc/covenant/programs/covenant/src/instructions/init_config.rs:32-49`

- **Exploit:** A malicious/compromised admin sets min_bond_bps far above 10_000 (raise_dispute then demands a bond larger than the escrow, making disputes economically impossible and effectively disabling poster protection), or sets max_challenge_period to an enormous value so a job created with the max challenge period locks escrow indefinitely. ### accept_job allows the poster to accept their own job as taker
- **File:** `/Users/baturalpguvenc/covenant/programs/covenant/src/instructions/accept_job.rs:26-39`
